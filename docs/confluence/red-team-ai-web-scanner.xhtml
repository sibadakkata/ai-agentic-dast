Red Team AI Web Scanner

Canonical technical reference for the AI DAST Scanner platform (May 2026). Audience: security architecture reviewers, AppSec testers, Red Team, and internal product teams running authorized assessments.

1. Overview

The Red Team AI Web Scanner is an internal, LLM-driven Dynamic Application Security Testing (DAST) platform. An autonomous agent reasons about each target application, discovers attack surface (SPAs, forms, APIs), generates context-aware payloads, and executes multi-phase security tests using Playwright and HTTP tooling. Findings, evidence, and live telemetry are persisted to PostgreSQL and streamed to the UI in real time.

What it does: Orchestrates authorized web/API security scans with passive recon, crawling, and OWASP-aligned vulnerability phases (XSS, SQLi, SSRF, IDOR/BOLA, CSRF, auth flaws, and more). Supports Postman and Burp imports, multiple auth modes, and selectable LLM models on AWS Bedrock.

Who it is for: Red Team, Application Security, and internal product teams who need self-service, repeatable DAST against staging or lab targets (with appropriate authorization).

Status: Production soft launch as of May 2026 — ALB + WAF ingress, Fargate-per-scan workers, RDS PostgreSQL Multi-AZ primary store, weekly S3 backups. HTTPS on the ALB is pending corporate TLS certificate issuance; HTTP is used during soft launch behind WAF rate limits.

5. Data flow (single scan)

  1. User authenticates via ALB to the UI using HTTP Basic (DAST_AUTH_USER / DAST_AUTH_PASS environment variables on the UI container).
  2. User submits POST /api/scan with target URL, profile, scope, intensity, and model.
  3. UI inserts a scan row in PostgreSQL (status=queued) and publishes initial live_events.
  4. UI calls ecs:RunTask with task definition dast-scanner-runner:5, passing SCAN_ID and job JSON via container environment overrides.
  5. Fargate task pulls the runner image from ECR through VPC endpoints.
  6. Task retrieves the RDS password from Secrets Manager (VPC interface endpoint, IAM task role).
  7. Task connects to RDS over private VPC networking.
  8. Task subscribes to Redis and publishes live events as phases progress; events are also durably logged to PostgreSQL.
  9. Task reaches target pages/APIs via assigned public IP (outbound HTTP/HTTPS).
  10. Task invokes Amazon Bedrock for LLM reasoning, tool use, and payload generation.
  11. Findings are written to the findings table; aggregated JSON to scan_results; telemetry to Redis + live_events.
  12. UI streams events to the browser via GET /api/scans/{scan_id}/stream (SSE), replaying from PG and subscribing to Redis.
  13. Task exits on completion or cancellation; UI reads final status from PostgreSQL.

6. Security model

Network

All sensitive data-plane services (RDS, Redis, Secrets Manager) reside inside the VPC and accept connections only from approved security groups: EC2 UI, Fargate runner tasks, and the backup Lambda. The ALB is the sole public entry point for the UI. The EC2 security group blocks direct port-80 ingress from the Internet; only the ALB security group is permitted.

WAF

  • AWSManagedRulesCommonRuleSet
  • AWSManagedRulesSQLiRuleSet
  • AWS IP reputation and anonymous IP managed lists
  • Rate-based rule: 2000 requests per 5 minutes per IP

Authentication

Current: HTTP Basic authentication via environment-injected credentials on the UI container. Credentials are distributed through a secure channel (not documented here).

Planned: Internal SSO via SAML/OIDC (pending IT integration). No public self-registration.

Data protection

  • At rest: RDS encryption, S3 backup encryption, Secrets Manager for credentials.
  • In transit: ALB HTTPS pending corporate TLS certificate (soft launch uses HTTP on ALB); VPC-internal traffic stays private. Bedrock and target HTTPS use TLS.
  • Audit: CloudWatch logs (ALB access, WAF, Lambda, ECS task stdout). PostgreSQL live_events provides a per-scan audit trail.
  • Secrets handling: Never embedded in container images, committed task definitions, or git. Runtime retrieval via Secrets Manager and IAM roles. Local .env on EC2 is mode 600 and git-ignored.

Only scan targets you are authorized to test. The scanner performs active attacks (injection, auth bypass probes, etc.). Misuse may violate policy and law.

Phase overview (vulnerability_scan)

  • Passive recon: TLS configuration, security headers, JavaScript library/CVE hints, technology fingerprinting (runs around the phase loop).
  • SPA / site crawl: Discovers routes, forms, parameters, and API endpoints within scope.
  • XSS probes: Reflected/stored/DOM-context testing with generated payloads.
  • SQLi probes: Error-based, boolean, and time-based inference on parameters and APIs.
  • SSRF probes: Out-of-band and inline callbacks where applicable (API SSRF phase).
  • IDOR / authorization: Horizontal and vertical privilege tests with secondary credentials when supplied.
  • CSRF detection: State-changing requests without anti-CSRF tokens.
  • Auth/session: Weak session handling, credential flows, JWT issues.
  • Runtime verification: Re-tests high-confidence findings to reduce false positives before reporting.

Choosing a model and budget (new — May 2026)

  • Manual (unchanged): Pick one model (Haiku, Sonnet, or Opus) for all phases.
  • Auto mode: The platform selects Haiku, Sonnet, or Opus per phase to balance cost and quality.
  • Opus on hard phases: Auto invokes Opus for demanding reasoning (access control, business logic, session management, attack chains).
  • Budget default: Auto mode applies a server-side cap of $30 USD per scan by default.
  • Custom cap: A higher or lower per-scan budget can be set only in the Web UI scan form (not via API/MCP/OpenClaw).
  • Budget gate: When spend hits the cap the scan pauses; only the scan starter or an admin can approve additional budget in the Web UI.

For automation usage (MCP, OpenClaw, REST API) see the Red Team AI Web Scanner — Automation: MCP, OpenClaw, REST API child page. Deep-dive in Git: docs/intelligent-model-selection.md and docs/automation-mcp-openclaw-api.md.

8. Usage

URL: http://rt.ai.webscanner.gendigital.com/ (after DNS CNAME is active) or http://dast-scanner-336692728.us-east-2.elb.amazonaws.com/ (always resolves).

Login: HTTP Basic. Credentials are shared via secure channel (not in this document).

Trigger a scan: Use the dashboard form or POST /api/scan with JSON (see sample). Use only authorized targets.

View results: /scans/{id} (UI), /api/results/{id} (JSON), /api/results/{id}?enc=b64 (base64 envelope for clients that cannot handle raw binary in JSON).

Cancel a scan: POST /api/scan/{scan_id}/stop (transitions scan to cancelled; Fargate task receives stop signal via DB/Redis).

  • Backup: Lambda dast-scanner-db-backup weekly (Sunday); PostgreSQL dump to tar.gz under backups/yyyy/mm/dd/ in S3.
  • Restore: Manual pg_restore from tar.gz, or restore RDS snapshot in AWS console.
  • Monitoring: CloudWatch dashboards (Fargate, ALB, RDS). ECS logs: /ecs/dast-scanner-runner. Lambda logs: /aws/lambda/dast-scanner-db-backup.
  • Scaling: Demand-driven — one Fargate task per active scan; no idle worker pool. Bounded by regional Fargate vCPU quota (~10K vCPU).

LLM agent design

Each scan is driven by a tool-using LLM agent (LiteLLM router to Amazon Bedrock). The agent receives structured system prompts per phase, maintains conversation context for the target, and invokes tools for HTTP requests, Playwright navigation, payload submission, and finding registration. Phases run sequentially (or in parallel for multi_agent profile) with defensive logging: every phase appends to phase_log even on worker failure, preserving auditability. Transient Bedrock errors (throttling, 502/503/504, connection resets) are retried with exponential backoff; terminal errors (content filter, context window exceeded) fail fast.

Persistence schema (conceptual)

  • scans — scan metadata, status, configuration snapshot, timestamps.
  • findings — normalized finding rows (severity, title, URL, evidence references).
  • scan_results — large JSON blob (full agent output, test log excerpts).
  • live_events — ordered event stream for UI replay and forensics.
